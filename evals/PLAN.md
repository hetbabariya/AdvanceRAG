# Evaluation Pipeline Plan — AllInOneRAG

> Local-first RAG evaluation pipeline built on **DeepEval** with an **OmniRoute** judge.
> Scope for v1: local CLI only — no CI, no YAML experiment configs, no production monitoring.

---

## 1. Goals

- Evaluate the **real pipeline code path** (`RagService`: rewrite → retrieve → rerank → generate), not a notebook copy.
- Produce a **reviewed golden dataset** generated by an LLM from a fixed benchmark corpus, curated by hand.
- Get **stage-level diagnosis**: know whether failures come from chunking, retrieval, reranking, or generation.
- Enable before/after comparisons when changing pipeline knobs (chunking, top_k, query rewrite, models).

## 2. Locked Decisions

| Decision | Choice |
|---|---|
| Framework | DeepEval (custom harness scripts; Synthesizer NOT used) |
| Judge + generator LLM | OmniRoute (`OMNIROUTE_BASE_URL` / `OMNIROUTE_MODEL` / `OMNIROUTE_API_KEY`, OpenAI-compatible) |
| Eval invocation | In-process `RagService` adapter (primary); HTTP mode deferred |
| Caching | Redis answer cache bypassed during eval runs (`QUERY_CACHE_ENABLED=false`) |
| Corpus | Fixed benchmark docs, **local-only** (`evals/corpus/` gitignored); d2l book trimmed to ~5 chapters |
| Golden set | ~50–60 LLM-generated candidates → human Streamlit review → `datasets/golden.json` (committed) |
| Metrics | ContextualRecall · ContextualPrecision · Faithfulness · AnswerRelevancy |
| Out of scope (v1) | CI gates, experiment YAMLs, regression baselines, production feedback loop |

## 3. Why a Fixed Benchmark Corpus?

AllInOneRAG accepts any user upload, but evaluation requires known inputs:

1. **Ground truth** can only be authored against documents you've read.
2. **Comparability** — regression detection is only valid if every run sees identical questions over identical content.
3. **Reproducibility** — failing cases must be re-runnable exactly.

The corpus *stands in* for real uploads by covering the variety of document types users bring.

## 4. Benchmark Corpus (local only)

| File (renamed) | Source | Stresses |
|---|---|---|
| `book_d2l_subset.pdf` | Dive into Deep Learning (`https://d2l.ai/d2l-en.pdf`, CC BY-SA 4.0) — trimmed to ~5 core chapters | Long structured doc: heading hierarchy, math+code+prose, cross-section retrieval |
| `report_msft_10k_2024.pdf` | Microsoft FY2024 Form 10-K (public SEC filing) | Tables + exact-number lookup; where naive chunking silently fails |
| `paper_attention.pdf` | "Attention Is All You Need" (`https://arxiv.org/pdf/1706.03762`) | Dense academic: formulas, ablations, multi-hop Qs |
| `paper_rag.pdf` | Lewis et al. 2020 (`https://arxiv.org/pdf/2005.11401`) | Same axis; thematically on-topic |
| `short_wiki_rag.pdf` | Wikipedia "Retrieval-augmented generation" PDF export | Short simple doc sanity baseline |

Rules:
- Frozen under `evals/corpus/` (gitignored). Swap a doc → regenerate only that doc's pairs.
- Ingested under a dedicated `eval-bot` user so goldens pin to stable `file_id`s and never pollute real accounts.

## 6. Golden Dataset

### Generation (LLM, not DeepEval Synthesizer)

```
corpus PDF → backend's own loader/chunker (same code path as production)
   → stratified chunk sampling per doc
   → OmniRoute writes 1–2 QA pairs per chunk, grounded ONLY in that chunk
   → datasets/candidates_raw.json
```

Question-type mix (~50–60 total):

| Type | Purpose |
|---|---|
| factual | single-chunk lookup baseline |
| multi_hop | two related chunks combined (same section/adjacent) |
| summary | section/document-level comprehension |
| unanswerable | plausible question the doc cannot answer → correct behavior is refusal; catches hallucination |

### Golden record schema

```json
{
  "input": "question",
  "expected_output": "ground-truth answer",
  "context": ["source chunk text"],
  "metadata": {
    "source_doc": "report_msft_10k_2024.pdf",
    "section": "...",
    "question_type": "factual | multi_hop | summary | unanswerable"
  }
}
```

### Human review gate

Streamlit app lists each candidate (question | expected answer | source chunk) with Approve / Edit / Reject.
Nothing enters `datasets/golden.json` without review — garbage goldens make every metric meaningless.

## 7. Judge Model

```python
# evals/judge_model.py
class OmniRouteJudge(DeepEvalBaseLLM):
    # wraps langchain_openai.ChatOpenAI(
    #     model=OMNIROUTE_MODEL, api_key=..., base_url=OMNIROUTE_BASE_URL, temperature=0)
    # generate(prompt, schema) parses into DeepEval's Pydantic schemas
```

- Required because DeepEval defaults to OpenAI GPT otherwise; one instance passed to all metrics.
- Built-in smoke test verifies structured JSON output works before any long run.

## 8. Eval Runner Flow

```
datasets/golden.json
   │ EvaluationDataset.add_goldens_from_json_file()
   ▼
for each golden: RagService (rewrite → retrieve → rerank → generate)
   │  cache bypassed; capture answer, retrieved chunk texts, stage latencies
   ▼
LLMTestCase(input, actual_output, expected_output, retrieval_context)
   ▼
evaluate(test_cases, metrics=[
    ContextualRecallMetric(model=judge),
    ContextualPrecisionMetric(model=judge),
    FaithfulnessMetric(model=judge),
    AnswerRelevancyMetric(model=judge)])
   ▼
console score table (overall + per doc_type) + results/run_<timestamp>.jsonl
```

Note: DeepEval has no Recall@K/MRR/NDCG; its retrieval metrics are LLM-judged contextual ones.

## 9. Diagnostic Mapping — what scores tell you to fix

| Symptom | Root cause | Fix area |
|---|---|---|
| Low ContextualRecall | needed info not retrieved at all | chunking strategy, top_k, hybrid weights |
| Good recall, low ContextualPrecision | right info present but buried | reranker, ordering, top_k trim |
| Good retrieval, low Faithfulness | answer not grounded in context | prompt, context packing |
| Low AnswerRelevancy | answer misses the question | query rewrite, generation prompt |

Per-doc-type breakdown adds another layer (e.g., strong on books, weak on table-heavy reports → table-aware chunking is the next improvement).

## 10. Build Order

1. **Phase 0** — `corpus_prep.py`: move/rename PDFs into `evals/corpus/`, extract d2l subset chapters.
2. **Phase 1** — `config.py` + `judge_model.py` (+ OmniRoute JSON-mode smoke test).
3. **Phase 2** — `generate_dataset.py` → candidates from all 5 docs.
4. **Phase 3** — `review_app.py` → human curation → `golden.json`.
5. **Phase 4** — `run_eval.py` + cache-bypass flag + eval-bot bootstrap → baseline run.

~500 LOC total. No other backend changes besides the optional cache flag.

## 11. Usage Workflow

```bash
pip install -r requirements-dev.txt      # adds deepeval
python -m evals.corpus_prep              # once: corpus files ready
python -m evals.judge_model              # smoke test OmniRoute
python -m evals.generate_dataset         # whenever corpus changes
streamlit run evals/review_app.py        # curate → commit golden.json
docker-compose up -d                     # postgres + redis
python -m evals.run_eval                 # baseline scorecard
# ...change pipeline knobs...
python -m evals.run_eval                 # compare tables manually → decide what improved
```

Prerequisites running before `run_eval`: Postgres + Redis (docker-compose), Pinecone key, OmniRoute up, keys in `.env`.

## 12. Success Criteria

- [ ] Smoke test: OmniRoute returns schema-valid JSON for a metric prompt.
- [ ] Generator produces ≥40 reviewable pairs across all 4 question types and 5 docs.
- [ ] Baseline run completes with scores for every golden.
- [ ] Unanswerable cases expose refusal behavior signal.
- [ ] A/B sanity check (e.g., `QUERY_REWRITE_ENABLED=false` vs `true`) produces visibly different retrieval metrics — proving the harness measures what it claims.
